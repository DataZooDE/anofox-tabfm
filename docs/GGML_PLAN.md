# Plan: move the CPU engine from ONNX Runtime to ggml (correctness first, ORT as oracle, then optimise to ORT parity)

> **Status (2026-11-21): done and superseded in places.** The CPU device is always ggml and the ORT CPU engine, the `TABFM_CPU_ENGINE` option and the vcpkg ORT port are removed
> (see "P6 follow-up" and "P8 result" below). Mentions of `TABFM_CPU_ENGINE`, `TabFMSessionConfig::cpu_engine` and an ORT oracle build in the sections written before that describe the migration path, not the current build.

## Context
ORT's source is gone from GitHub (vcpkg port 404, main CI red since the outage), the CPU build needs a heavy vcpkg ORT build, and
the CPU, CUDA, ROCm and MLX paths are four unrelated stacks. A spike (throwaway spike, not committed) ran the full Nori 1.5
graph (12,592 nodes, 52 op types) through ggml matmul under a host interpreter: correct (max|d| vs eager PyTorch 0.463, ORT itself
0.459) and at ORT speed (2.9-3.1 s vs 2.9-3.0 s, loaded machine). Goal: ggml becomes the CPU engine, vendored as a git submodule
(no third-party release hosting at build time), with the current ORT implementation kept as the oracle until every model passes.

Decisions (user): **compile-time selector only** (no new runtime setting); **lower every op to ggml graphs** (not host kernels
under an interpreter). Consequences, stated up front:
- ggml graphs are static-shape and max 4-D. The ONNX graphs compute shapes at runtime, so a host-side **shape/constant evaluation
  pass** per input-shape signature must run first, then ONE ggml graph is built per signature and cached. Inherent to lowering.
- 16 of 38 graphs use rank-5/6 tensors (nori15, orion-*, tabicl, kumo, causilo, tabpfn3/35). A **rank-reduction pass** (drop size-1
  dims, merge adjacent dims) fixes most (5 of 8 sampled graphs reach <= 4-D; nori15 78 tensors, orion-msp 36, orion-bix 12 do not).
  Residual rank-5 ops become ggml **custom ops** (`ggml_custom_4d` / `ggml_map_custom*`, host kernel inside the graph).
- ggml has no native Where, comparisons, ScatterND, GatherND, GatherElements, Mod, IsNaN/IsInf, Range, or NaN-aware int arithmetic.
  Where must NOT be emulated with arithmetic (NaN*0 = NaN; the graphs mask with NaN). These become custom ops, or are evaluated on
  the host in the shape pass when they only feed shapes. Coverage is verified against the vendored ggml header (P1), not assumed.
- Compile-time selection means one binary has one CPU engine. Differential tests therefore build BOTH backends into the test
  binary (ORT + ggml) and compare in-process; the extension's own device-cpu path uses the flag's choice. CI runs the full SQL
  suite on a build per engine until ORT is removed.

## P1 result (coverage matrix, done)
`docs/GGML_LOWERING.md` classifies all 72 ops of the 45 bundled CPU graphs (402,814 nodes); the current split by kind is the first table
there (generated). After the crew review (below) Clip moved from COMPOSITE to CUSTOM (ggml_clamp turns NaN into the bound), TopK stays
COMPOSITE but via argsort (ggml_top_k is unordered), Pad became COMPOSITE (zero-fill only).
So "lower everything" stays tractable: the custom-kernel set is 24 ops but a small share of the graph. Caveats: node share is not
cost (Where and the comparisons sit on the attention-mask paths), Pow is CUSTOM only for its 9 dynamic-exponent nodes (4,259 of
4,268 use a constant exponent 2, 0.5 or 3), and the plain graphs contain `Relu`, which the ext graphs do not. The custom set is
pinned by `test_tabfm_ggml_lowering.cpp`; the doc is regenerated by `tools/ggml_parity/gen_lowering_doc.py`.

## Pre-P2 experiment result (graph-build cost and memory on the real Nori 1.5 graph; throwaway code, not in the repo)
Method: run the n-D interpreter at T=128/512/2048 (train = 0.7 T, 10 features), record every node's shapes, then build a ggml graph
from the recording with no compute: matmul as `ggml_mul_mat`, Transpose as permute+cont, reshapes as aliases, every other float node as
a `ggml_custom_4d` placeholder of the right output shape, integer/shape nodes folded on the host, then `ggml_gallocr_reserve`.
| T | host int/shape nodes (6,545) | ggml graph build (7,559 nodes) | gallocr arena | ORT peak RSS | ORT run |
|---|---|---|---|---|---|
| 128 | 6 ms | 3 ms | 15 MB | 400 MB | 0.5 s |
| 512 | 10 ms | 2 ms | 115 MB | 942 MB | 2.1 s |
| 2048 | 32 ms | 2 ms | 1,610 MB | 5,181 MB | 9.7 s |
Correction after the review round: the first ORT column (peak RSS 5,181 MB at T=2048) came from a process that ran twice and
included Python/ORT import overhead. Re-measured in a fresh process with VmHWM (baseline 54 MB, 295 MB after loading the session,
arena on or off): ORT's run adds ~320 MB at T=512 and ~2.4 GB at T=2048 (peak 2.7 GB). So ggml's planned intermediate arena
(115 MB / 1.6 GB) is roughly 1.5x smaller than ORT's run, not 3x, and the placeholder model errs in both directions (custom ops get no
in-place reuse and MatMul inputs get extra copies, which inflate it; no repeat/cast/rank-5 handling, which deflates it), so treat it as
indicative only. Weights are not free either: ggml's mul_mat needs the right operand as [n][k] while ONNX stores [k][n], so a
transposed resident copy (~296 MB for Nori 1.5) or a pre-transposed weight store is needed; "borrowed, no copy" holds only for weights
that can be used as they are.
Findings that survive: (1) building a graph per input shape costs milliseconds (3 ms for 7,559 nodes, plus a 6-32 ms host shape pass)
against seconds of compute, so a per-signature cache is an optimisation, not a requirement (the 2 ms contains no real lowering logic, so
re-measure in P4); (2) the naive interpreter is slower than ORT at large T (16 s vs 10-12 s at T=2048), a P7 matter.

## P2 result (shape pass and rank reduction, done)
`src/tabfm_shape_eval.cpp` evaluates shapes and the integer/bool values derived from them for a concrete input shape (52 ops, the ones
Nori 1.5 uses; other ops are refused by name until their model lands in P4). All 2,520 sampled tensors of the real Nori 1.5 graph match
ONNX Runtime's shapes at six (rows, train, features) combinations (odd feature counts, features = 1, train = 1), and ~6,400 integer tensors per combination match ORT's values (data-dependent mask tensors are not folded and are skipped); mutation checks go red. A review round added float32 rounding (int(float32(10)*0.7f) is 7, not 6), exact/wrapping integer arithmetic, narrow-int Cast wrapping, IsInf flags, NaN-propagating Max/Min, refusals for zero divisors, zero steps and malformed axes, and a cap on materialised constants. Goldens:
`test/fixtures/ggml_shapes/` from `tools/ggml_parity/gen_nori15_shape_goldens.py` (shapes only, no weights).
`src/include/tabfm_rank_reduce.hpp` coalesces broadcast operands (drops shared size-1 dims, merges neighbours every operand treats alike),
property-tested against a naive n-D broadcast add. Census on Nori 1.5 (T=130): of 6,433 float tensors 407 have rank > 4 and 78 still have
five real dimensions (max 5) after dropping size-1 dims: those need an op-aware merge or a custom op in P3.

## P3 result: all 72 ops lowered; P4 started with Nori 1.5 matching ORT
- **State:** every op in the lowering table is implemented (72/72) and every one of the 45 bundled CPU graphs is free of missing ops. 439 ORT goldens
  (`test/fixtures/ggml_ops`, generated by `tools/ggml_parity/gen_op_goldens.py`, ORT graph optimisation OFF) pass at 1, 2 and 7 threads; exact ops
  bit for bit (signed zero included), accumulating ops with a wide band. 309 `[tabfm]` test cases green.
- **Nori 1.5 whole model (P4, first model):** `test/cpp/test_tabfm_ggml_nori.cpp` (local only: `TABFM_NORI15_DIR`, real weights, never committed) runs the real
  graph through `GgmlRunGraph` with the 381 safetensors weights pointed at in place (no copy) and compares with ORT at 9 configurations (T 5..200, features
  1..17, train 1..150, NaN features): max |diff| 4e-7 .. 5e-3 on logits of rms 1..25, i.e. ORT's own noise floor (ORT vs ORT with other threads/optimisation
  differs by up to 2e-3). Time on this machine (4 threads, not yet optimised): 0.07 s (T=9), 0.33 s (T=60), 0.78 s (T=130), 2.1 s (T=200).
  `[ggml_nori_probe]` (env `TABFM_NORI15_PROBE=<tag>`) compares ~6,000 intermediate tensors with ORT's and names the first that differs: that is how the
  float64 problem below was found (it needs `probe_ref.py`, kept in the scratchpad).
- **Mechanisms added in this round:**
  - *More than four dimensions:* tensors are contiguous row-major, so adjacent dimensions merge for free. Each op regroups its operands into at most four
    groups (`As`/`Unfold`): elementwise ops via the broadcast coalescer (and, when more than four interleaved groups remain, by materialising each operand
    at the output shape with one 3-group repeat per axis), axis ops as `[before, axis, after]`, Transpose by merging the runs of the permutation, Reduce by
    merging reduced/kept neighbours (one axis at a time when they alternate into more than four groups), Slice by merging uncut neighbours, MatMul by
    coalescing the batch dimensions. Flat-memory kernels (Pad, CumSum, GatherND, ScatterND, ScatterElements, GatherElements, dynamic Gather) take the
    logical shapes in a plan and do not care about the rank. Refused by name: a transpose with more than four runs, more than four cut groups, etc.
  - *Integers computed from float data* (TopK indices, Cast float to int64, embedding indices) live in the graph as exact floats (< 2^24), like the bool masks;
    Cast float to int truncates toward zero, integer Mod with fmod=0 takes the sign of the divisor.
  - *Float64 islands:* the Nori graph casts to DOUBLE for its per-feature Gaussian encoder and extracts exponent digits with floor(log(x)/log(10)), which
    float32 gets wrong at exact powers of ten. ggml has no usable float64 kernels, so each double-typed node is a custom op that runs the shape pass's
    element-wise interpreter (same code, ORT-checked, now with an F64 dtype that skips float32 rounding and an unlimited-size `EvaluateNode`) on its
    operands at inference time; intermediate double tensors are real float64 ggml tensors. Limit: ORT's own double `Log` is within 1-2 ulp of libm, so a
    `floor` landing exactly on an integer is implementation-defined and cannot be matched (documented in the generator).
  - *Empty tensors:* a node with an empty output is skipped; Concat drops empty operands; any other consumer is refused by name.
- **Where ggml/our first guess disagreed with ORT (found only because goldens carry NaN/inf):** `ggml_sgn`/`ggml_relu` map NaN to 0 (custom kernels);
  ORT Clip is `min(max(x, lo), hi)` with +-FLT_MAX defaults; Gemm ignores C when beta == 0; Where returns +0 for a selected -0; ReduceMax/Min visit elements
  in flat order and skip NaN unless it is first (and are SIMD-lane dependent for a mid-row NaN, so not matched there).
- **Crew review #1 (end of the first P3 slice) fixed:** recursive graph build (segfault at 20k nodes on a 256 KB stack) -> incremental build; unchecked
  context budget (abort) -> sized from lowered nodes + per-node reserve check that throws; input length check; thread clamp; Slice step overflow; lazy
  initializers; `NDEBUG` on the ggml targets (Debug builds abort on NaN softmax rows, reproduced standalone).
- **Deferred to P7 (performance):** weights copied/transposed per run (cache a pre-transposed leaf per initializer), cancelling Transpose+MatMul copies,
  broadcast materialisation (Sub/Div/And/Or/Expand, and the >4-group fallback), single-threaded custom kernels (mask chain, TopK, gathers, double nodes), a
  thread pool per call (needs ONE shared pool; DuckDB workers must not each take k threads), Concat O(n^2), Gather index replication.
- **Other known gaps:** no opset guard (the reader does not expose the opset; all bundled graphs are opset 18 - add it with the engine loader in P5);
  host-folded int64 outputs travel as floats in the runner; `Pad` supports `constant` mode with host-known pads and constant only; `GatherND` batch_dims = 0;
  Scatter ops `reduction=none`; `Slice` negative steps and steps on the innermost axis are refused; LayerNormalization Mean/InvStdDev outputs are refused;
  float16/bfloat16 tensors are treated as float32.
- **Next:** P4 for the remaining 44 graphs needs their real weights/references (the fixture graph and the random-init fixtures can run in CI today); then P5
  (engine integration: loader from safetensors by name, split prepare/query models, memory estimate, one shared thread pool, settings wording), P6 flip, P7 speed.

## P7 progress: performance against ORT (Nori 1.5, warm, 4 threads)
- Measured with `TABFM_NORI15_REPEAT` (best of N through one `GgmlExecutor`): **9 rows 8.4 ms (ORT 10), 60 rows 70 ms (55), 130 rows 187 ms (151), 200 rows 489 ms (412).**
  Where it came from (200 rows, 2.1 s -> 0.49 s): `Pow(x, 2)` as a multiply instead of a single-threaded libm loop (-0.5 s), row-partitioned multi-threaded custom kernels,
  tinyBLAS (`GGML_LLAMAFILE=ON`, matmul 552 -> 402 ms), zero-copy weight/input leaves (no 300 MB upload per call), a Transpose-then-MatMul peephole (the operand is read in the layout

  signature (shape pass + lowering + arena kept across calls), one thread pool for the session's life (paused between runs). Remaining at 200 rows: matmul 41% (AVX2 baseline against
  ORT's runtime-dispatched AVX-512; a native build made no measurable difference on this machine), CONT 19%, MUL 13%.
- A bug the executor exposed and a test now pins (`[ggml_graphs]` runs every graph twice on different data in fresh buffers): views (reshape/slice) of a re-pointed input leaf kept the
  previous call's absolute pointer; each such view is refreshed per run.

## P8 result: the ggml engine on GPUs (Nori 1.5 against ORT; spikes and a plugin, host wiring partly open)
- **How a GPU is reached.** `GgmlExecutorConfig::device = "gpu[:N]"`: weights are uploaded once into device memory, `ggml_backend_sched` splits the graph, and the custom kernels
  (TopK, Where, float64 islands...) stay on the CPU inside the same graph. `"cpu-sched"` runs the identical scheduler path on the CPU, which is how the goldens and all 45 graphs
  check it bit-exactly without hardware. Three scheduler facts cost the time here and are pinned in `ExecuteCompiled`: (1) a leaf the scheduler allocates itself can land in a host
  buffer and reach the device through a split-input copy (one-element constant read back as 0), so every input/constant leaf is pinned to the device backend; (2) the scheduler
  **rewrites `node->src` in place**, so a graph must be split and allocated once (no `reserve` + `alloc` on the same graph; later runs only upload inputs and compute), otherwise
  a CPU op reads a stale, never-refreshed copy tensor; (3) a device weight buffer is marked `USAGE_WEIGHTS` so ops are placed where their weights live.
- **Results** (`tools/ggml_parity/ggml_driver.cpp --device gpu`, real Nori 1.5 weights, max |logit diff| vs ORT; logits rms 11.6 at 200 rows):
  | device | 455 op goldens | Nori diff, 200 rows | warm, 200 rows | CPU engine, same machine |
  |---|---|---|---|---|
  | AMD Radeon 890M (gfx1150, HIP) | 451 (4 are 1e-5 float rounding) | 1.5e-3 | 0.49 s | 0.55 s |
  | NVIDIA RTX 4090 (CUDA 12.4), `NVIDIA_TF32_OVERRIDE=0` | 444 (rounding; sin/cos of spiked arguments) | 3.4e-3 | 0.15 s | 0.55 s (x86 host) |
  | Apple M3 (Metal) | 449 | **3.25** | 0.57 s | 0.80 s (CPU, 3.7e-3) |
  The CUDA default is **TF32** matmuls on Ampere+ (about 2e-3 relative per matmul, up to 1.5 on the logits): the plugin sets `NVIDIA_TF32_OVERRIDE=0` for `precision='fp32'`
  (same contract as the ORT-CUDA plugin). **Metal is not accurate enough**: ggml's f32 matmul kernel stages tiles in half precision and the Metal backend has no switch for it, so
  macOS GPU stays on the MLX plugin; ggml-Metal is not shipped. The Apple-silicon **CPU** engine (NEON) matches ORT and was built and run on macOS here.
- **The plugin** (`src/tabfm_ggml_plugin.cpp`, built by `tools/ggml_plugin/CMakeLists.txt` with `-DTABFM_GGML_GPU=cuda|hip`) implements `tabfm_plugin_abi.h`, reads weights straight
  from the memory-mapped safetensors by the staged graph's external offsets, and is `libanofox_tabfm_ggml-cuda_plugin.so` / `libanofox_tabfm_ggml-rocm_plugin.so`; the host (`TryGgmlGpuBackend`, tabfm_engine.cpp) prefers it over the ORT/MIGraphX
  plugin when it is in `anofox_tabfm_ep_path`, on the plain `ext` graph. `tools/ggml_plugin/abi_check.cpp` loads it through the ABI and compares with ORT (verified on the gfx1150 build: 8.8e-5 at 24 rows, 1.5e-3 at 200).
- **Host wiring (done).** `TryGgmlGpuBackend` (tabfm_engine.cpp) runs before the MIGraphX/CUDA branches and engages only when `libanofox_tabfm_ggml-{cuda,rocm}_plugin.so` is in
  `anofox_tabfm_ep_path`; it takes the plain `ext` graph (so the masked MIGraphX graph is not needed), and an explicit `cuda`/`rocm` request counts the card as usable
  when that plugin is installed (MIGraphX's arch allowlist excludes e.g. the gfx1150 iGPU). **End to end through SQL on ROCm** (`tools/gpu_test/scenarios/ggml_plugin_gpu.sql`,
  Nori 1.5, real weights): `tabfm_models()` reports `rocm:0` and the regression agrees with the CPU engine to 6.6e-5 at scale 7.0. **CUDA plugin binary** built on an RTX 4090
  (CUDA 12.4, sm_89) and checked through the ABI: fp32 3.4e-3, tf32 0.2 (so the precision switch works), bf16 refused.
- **SQL on CUDA (done).** The extension was built on the RTX 4090 pod and `ggml_plugin_gpu.sql` run: `tabfm_models()` reports `cuda:0` and the 100-row Nori regression agrees with the
  CPU engine to **0.031 at scale 7** (0.4%), looser than ROCm's 6.6e-5. Cause: this table has 4 features, so its small matmuls take ggml's own tensor-core kernel
  (`mul_mat_f`, 16 or fewer columns), which `NVIDIA_TF32_OVERRIDE=0` does not reach; the large-matmul runs above are 3.4e-3. Strict fp32 on CUDA for small tables needs a ggml change.
- **Weights at create (done).** `GgmlExecutor::PreloadWeights()`, called by the plugin's create, uploads every float32 external weight up front (a device that cannot hold the model fails at load).
- **Still open.** The plugin is not a release
  asset and has no CI job; `tabfm_devices()`/`tabfm_backends()` do not list the ggml lane (explicit `cuda`/`rocm` only, `auto` never picks it); Windows and Vulkan plugins; fp32 is not strict for matmuls of 16 or fewer columns on CUDA (ggml's own TF32 kernel has no switch).

## P3 design notes (from the post-P2 crew review)
- **The 78 five-real-dimension tensors** have only four shapes at T=350, H=17: (rows, features, 2, heads, head_dim) and variants, i.e. a fused
  projection reshaped to [R,F,2,h,hd]. Rule: keep (R,F) merged while in the fused layout (ggml ne = [hd, h, 2, R*F]), take the size-2 axis
  with a `ggml_view_4d` (offset only), unfold R*F afterwards (also a view; ggml_view_4d takes arbitrary strides). Slice first, unfold after.
  A merge is invalid when an op acts on one axis inside a merged group, a Transpose separates or reorders group members, or operands
  broadcast the pair differently. Rank reduction therefore needs a per-tensor GROUP MAP, not only the broadcast coalescer.
- **Op-aware merge rules (TensorIterator style):** Transpose: coalesce perm runs with perm[i+1] == perm[i]+1, fall back to a custom op if
  more than 4 groups remain. MatMul: batch dims merge only if both operands share the broadcast pattern across the pair. Reshape: a view
  only for contiguous inputs and only across whole groups. Softmax/LayerNorm: axis must be a trailing group, else permute + cont. Reduce:
  reduced axes adjacent after a permute. Concat/Slice: along the outermost member of a group.
- **ggml mul_mat batch broadcasting** is block-style (A index is i12/r2, ggml-cpu.c ~1230), requires t1->ne[2] % t0->ne[2] == 0 (ggml.c
  ~3352), output batch = B's batch. So the broadcast dim must be the INNER member of a merged pair; A=[1,h] against B=[R,h] needs a repeat
  or a per-slice loop; A with the larger batch needs B repeated. The weight operand needs cont(transpose(W)) (ggml_is_transposed assert),
  attention P@V needs V^T cont, permuted activations need a cont (nb10 must be 4).
- **Custom ops (ggml_custom_4d):** run in graph order with a barrier between nodes and may read earlier outputs, BUT every tensor the kernel
  reads must be listed in args or the allocator frees/aliases it; at most 9 args; n_tasks is capped at n_threads and the kernel must
  partition by ith/nth itself (or use n_tasks = 1).
- **Graph size:** GGML_DEFAULT_GRAPH_SIZE is 2048; use ggml_new_graph_custom (>= 16k nodes) and count ggml_graph_overhead_custom plus
  per-tensor overhead for 20k+ tensors in the context. Views are not allocated but keep the parent alive until all views die, so many
  strided views lengthen lifetimes.
- **NaN:** ggml_soft_max uses MAX(a,b) = a>b?a:b, so a NaN in a row makes the whole row NaN (same as ORT; verify with a golden, never by
  assumption); mul_mat picks different kernels by shape and thread count (accumulation order differs), so calibrate ggml-vs-ggml across
  thread counts. ggml_v_expf is a polynomial (ulp-level); softmax sums in double; ggml_norm is two-pass fp32: all within noise, none bit-exact.
- **Riskiest ops:** MatMul/Gemm/Einsum (layout asserts, copies, rank-5 batches), Transpose/Reshape with the group map, the mask chain
  Where + comparisons + And/Not/IsNaN (all attention masking, NaN-preserving), Slice/Gather/GatherElements/Concat (strided views, negative
  steps, int64 indices folded on the host), Clip/Min/Max/Pow (custom with NaN pass-through on the normalisation path).
- **Implementation order (earliest Nori 1.5 end to end):** plumbing (Constant, Shape, Identity, Squeeze, Unsqueeze, Reshape, Cast) ->
  Transpose + group-tracking rank reduction, MatMul, Add/Mul/Sub/Div -> Softmax, LayerNorm, ReduceMean/Sum -> Where + comparisons + IsNaN
  as custom kernels -> Slice, Gather, Concat, Expand -> Sqrt/Exp/Log/Tanh/Sigmoid/Pow/Clip/Erf -> the rest by Nori node count. Gate each op by
  swapping it into the working host interpreter (the spike) and comparing whole-graph output, so every step has a green reference.

## Ground rules (CLAUDE.md)
- Red-green TDD: every phase starts with a failing test. Error paths are first-class and name the fixing SET/CALL.
- Shared scaffold files (CMakeLists source list, anofox_tabfm_extension.cpp, tabfm_registration.hpp, tabfm_settings.cpp) change only
  with coordination; the selector avoids tabfm_settings.cpp by being a CMake option. The `anofox_tabfm_threads` description
  ("ONNX Runtime intra-op thread count") needs rewording, which IS in tabfm_settings.cpp: ask the user when reached.
- No OpenMP in the engine: libgomp spin-waiting starved ggml's thread pool in the spike (24 s -> 4 s with passive wait). Use ggml's
  threadpool only, sized from `anofox_tabfm_threads` / `tabfm_cpu_budget`.
- ORT stays the oracle until the end. The CUDA plugin keeps its own ORT-GPU core (PyPI wheel, already done), so "ORT gone" means
  gone from the CPU build and vcpkg, not from the CUDA plugin, until a later GPU migration.
- Docs and skills ship with code (rule 7). License wall unchanged: fixtures are random-init.

## Architecture
- `vendor/ggml` git submodule, pinned commit, CPU backend only, static, `GGML_OPENMP=OFF`, runtime CPU dispatch for distributables
  (`GGML_NATIVE=OFF` + dynamic variants; the spike used NATIVE=ON, which can crash on older CPUs).
- `src/tabfm_graph_ir.{hpp,cpp}`: backend-neutral IR from `tabfm_onnx_reader.cpp` (reused as is): topological nodes, initializers by
  NAME (borrowing the injected `TabFMTensorRef` buffers, no copy), last-use, op table.
- `src/tabfm_shape_eval.cpp`: host evaluation of all int/bool/shape tensors for an input-shape signature (Shape, Gather, Concat,
  Slice, Cast, Range, ConstantOfShape, comparisons, Where on ints). Output: concrete shape per tensor + folded constants.
- `src/tabfm_ggml_lower.cpp`: per-op lowering table `op -> native ggml | composite | custom` plus the rank-reduction pass.
- `src/tabfm_ggml_engine.cpp`: `GgmlBackend : TabFMBackend` (interface in `tabfm_ort_engine.hpp`), graph cache keyed by
  (graph, T, H, train_size, d), `ggml_gallocr` reuse, ggml threadpool. `SplitGgmlBackend` for prepare/query models (tabicl, kumo)
  mirrors `SplitOrtBackend` (tabfm_engine.cpp:777) incl. the context cache.
- `src/include/tabfm_ggml_ops.hpp`: `GgmlSupportedOps()` mirroring `tabfm_mlx_ops.hpp`, with a test that reads the lowering source and
  fails when they differ, and a test that every op in every bundled graph is covered (the MLX "missing ops" refusal pattern).
- CMake: `TABFM_CPU_ENGINE=ort|ggml` (default ort until the flip); `TABFM_WITH_GGML=ON` builds the ggml engine into the test binary
  regardless so parity tests run. Factories at tabfm_engine.cpp:1150/2002 (OrtBackend) and :1973 (split) pick by the flag.

## Test strategy (the oracle)
1. **Per-op goldens.** `tools/ggml_parity/` (uv project, like tools/export_*): one tiny ONNX per op and edge case via `onnx.helper`,
   random + adversarial inputs (NaN, +-inf, INT64_MAX, negative axes/indices/steps, rank-0, size-1 and size-0 dims, broadcast both
   ways, ints vs floats); **onnxruntime** produces expected outputs; graph + inputs + outputs are committed with pinned sha256 (CI
   verifies, never regenerates, like test/fixtures). Tests in `test/cpp/test_tabfm_ggml_ops.cpp`. They survive ORT's removal.
2. **Tolerances are calibrated.** `tools/ggml_parity/noise_floor.py` measures ORT vs ORT (graph optimisation off, different thread
   counts) per model; the gate is a small multiple of that floor (Nori 1.5: ORT is already 0.459 from eager at output std 66, so a
   fixed 1e-4 would fail a correct engine). Classification gates on label agreement and max prob difference.
3. **Whole-graph parity, in-process.** `test/cpp/test_tabfm_ggml_parity.cpp` builds the ORT session and the ggml session from the same
   graph bytes and initializers: committed fixtures in CI; real weights under `TABFM_REAL_WEIGHTS=1` for all 38 bundled graphs.
4. **SQL parity.** The existing sqllogictests run unchanged on each engine's build; golden values are engine-independent.
5. **Mutation checks** (as used for the Nori work): break an op or a pass on purpose and watch the test go red.

(2) fuse elementwise chains and Transpose->MatMul (permuted views, not copies); (3) pre-transposed weights WITHOUT a second resident
copy (the spike doubled weight RSS; tabfm-v1 is 6.6 GB, so measure, do not assume); (4) flash attention for rows^2 attention memory;
(5) thread tuning; (6) f16/bf16 weights where parity holds.

## Risks and open items
- Lowered-ggml is the larger route: custom-op count may dominate; graph-build time for 12k-21k nodes per shape (cache, measure in P4);
  ggml API churn (pin, wrap behind the IR); static-link footprint on Windows/macOS.
- Windows and macOS CPU builds are untested; P0 must compile there before P3.
- Tolerance calibration may show some models are noise-dominated (Nori: Log of tiny differences); the gate then moves to the metric
  (R2 / label agreement) with raw differences informational.
- Split models and the context cache (tabicl, kumo, orion) are the least-understood integration; P4 places them mid-sequence on purpose.
- If P1 shows most non-trivial ops are custom-only, revisit "lower everything" before P3 (the host-kernel interpreter from the spike
  is the proven fallback).
